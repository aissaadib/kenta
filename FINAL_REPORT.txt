============================================================
1. SUMMARY
============================================================
Kenta now runs on a Rust-owned capture engine with a real FFmpeg
segment buffer, working replay saves, manual recordings that finalize into
validated MP4 files, a persistent SQLite library, and a React interface
that reports actual backend state.

The previous implementation mixed polling, placeholder status, and
frontend-owned capture lifecycle. This pass replaced that layer rather
than rebuilding the product: existing Tauri/React/SQLite/FFmpeg
architecture, settings, and clip data were preserved.

Commits in this pass (local main):
  52bf2bc  Rewrite capture backend for reliable replay, recording, and settings
  5e94fcc  Rebuild the Kenta interface around real backend state
  (docs)   Document setup, data locations, and verified behavior

3. FUNCTIONAL FIXES
============================================================
Capture engine (src-tauri/src/capture.rs)
- Per-session temp directories, CSV segment tracking, replay-window
  pruning, export validation, and encoder fallback.
- Replay saves select the requested window and concatenate segments.
- Manual recordings record a session start time, stop FFmpeg with `q`,
  export the full session, then restart the buffer cleanly.
- Failed exports preserve their session directory for 24 hours.
- Output folder and replay-window changes apply without dropping buffered
  footage; capture-affecting changes restart the engine.
- Audio mixing supports microphone and loopback devices; missing devices
  produce warnings instead of broken commands.

FFmpeg helpers (src-tauri/src/ffmpeg.rs)
- Discovery via KENTA_FFMPEG/KENTA_FFPROBE, next to the exe, then
  PATH. No shell is used; all child processes receive argument arrays.
- Encoder availability parsing, dshow device parsing, duration probing,
  and concat-path escaping with unit tests.

Settings (src-tauri/src/settings.rs)
- Schema v2 with defaults for missing keys, corrupt-file recovery,
  reconciliation of out-of-range values, validation, and atomic-ish save.
- Monitor offsets stored as signed i32. Duplicate or reserved shortcuts
  are rejected.

Shortcuts (src-tauri/src/hotkey.rs)
- Dedicated Windows RegisterHotKey thread instead of polling.
- Parsing/normalization, conflict detection, and rollback when a new
  binding cannot be registered.

Storage (src-tauri/src/storage.rs)
- Correct SQL column mapping, get/update/delete APIs, escaped LIKE search,
  and tests for search, sort, rename path updates, and wildcard escaping.

Commands and lifecycle (commands.rs, lib.rs, worker.rs)
- Status payloads, settings apply/restart logic, clip operations,
  thumbnails, monitor enumeration, autostart, and hotkey commands.
- Rust starts capture at app startup and stops it on shutdown.
- Background worker handles hotkey actions and emits status snapshots;
  the frontend no longer polls.
- Tauri asset protocol is enabled with runtime allow_directory scoping for
  the clip folder and thumbnail cache only.

Interface (web/src)
- Typed IPC layer; fixed camelCase arguments for rename_clip and
  select_output_dir.
- Real shortcut capture (Esc cancels, Backspace clears, modifier-only
  combinations rejected).
- Numeric validation now tracks parent invalid state, blocks Save, shows
  field errors and a summary notice, remounts on preset/reset changes,
  and syncs render-time text with preset updates.
- "Show in folder" now uses Explorer's raw `/select,"path"` argument form;
  previously Rust quoted the whole switch and Explorer ignored it.
- Desktop-audio loopback warning is shown only when desktop audio is
  enabled. All selects have accessible labels.

8.1 PUBLIC RESEARCH (documented facts, not Medal internals)
------------------------------------------------------------
- Medal's own instant-replay page states that Medal is "always buffering in
  the background", saves "the last 15 seconds to 10 minutes", and uses F8 as
  the default save key. It also describes Auto-Clip and voice-triggered clips.
  https://medal.tv/learn/instant-replay-pc
- Medal's "How To Record and Make Clips" support article documents the clip
  length range and the buffer/clip workflow.
  https://support.medal.tv/support/solutions/articles/48001157618
- Medal's "Low Framerate (FPS), lag, or Choppy Clips" article recommends
  lowering resolution/FPS and using hardware encoding when capture hurts game
  performance.
  https://support.medal.tv/support/solutions/articles/48000922094
- Medal's "How To Choose Your Recording Method" and "Recommended Clip Quality
  Settings" articles document capture-method and bitrate/resolution trade-offs.
  https://support.medal.tv/support/solutions/articles/48001157616
  https://support.medal.tv/support/solutions/articles/48001159800
- Microsoft's WebView2 performance guidance documents the multi-process
  WebView2 model and recommends reducing renderer work rather than expecting a
  single-process memory footprint.
  https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance
- FFmpeg documents gdigrab as a GDI-based desktop capture device and ddagrab as
  a Desktop Duplication API filter.
  https://ffmpeg.org/ffmpeg-devices.html#gdigrab
  https://ffmpeg.org/ffmpeg-filters.html#ddagrab
- Microsoft documents Job Objects and JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, which
  terminates every process in the job when the last job handle closes.
  https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects
  https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information
- Tauri bundler 2.10.4 source (src/bundle/windows/msi/mod.rs) globs every *.dll
  in the release output directory into the MSI; a TODO in that source
  acknowledges this is broader than intended.

What this does NOT establish: Medal's internal capture API, encoder settings,
buffer format, or memory strategy. No claim about Medal internals is made here.

8.2 DIAGNOSIS (measurements on this machine)
------------------------------------------------------------
Contaminated baseline (before any fix):
- 7 orphaned Kenta FFmpeg processes whose parent Kenta processes were
  already gone. They held 1,412 MB working set / 4,338 MB private and were
  still writing into the replay buffer.
- 11 stale session directories / 2,334 MB in %TEMP%\kenta_buffer.
- Root cause: FFmpeg was spawned as a plain child with no Windows Job Object.
  When Kenta crashed or was force-terminated, Windows left the encoder
  running indefinitely. Duplicate launches created additional encoders and
  hotkey conflicts.
- Folder size: the workspace was 8,476 MB, but only 0.3 MB was web/dist and
  7.77 MB the recorded installer. target/debug alone was 6,252 MB and
  target/release 2,095 MB. The 8 GB was development build cache, not the app.
- Memory attribution: Kenta + WebView2 = about 397 MB working set at
  steady state; FFmpeg adds about 331 MB working set / 516-522 MB private.
  The user's "~400 MB" observation therefore matches the app+UI group exactly;
  the encoder is the additional cost.
- CPU attribution: FFmpeg consumed 12.4-13.6 s of CPU per 15-20 s wall time
  (roughly 0.6-0.9 of one core); WebView2 consumed the rest. Total idle CPU was
  3.7-5.0% of 20 logical CPUs, i.e. about one core. gdigrab is the hotspot.
- Capture backend comparison (10 s each, 1080p, h264_nvenc):
    gdigrab 60 fps: 7.75 s CPU, 338.9 MB peak WS, 525.9 MB private
    gdigrab 30 fps: 5.02 s CPU, 337.2 MB peak WS, 527.2 MB private
    gdigrab 720p60: 4.19 s CPU, 234.8 MB peak WS, 366.9 MB private
    ddagrab (all variants): failed immediately with
      "Selected output not supported" / "Generic error in an external library"
  ddagrab also failed with output_fmt=8bit/bgra, output_idx=1, draw_mouse=0,
  allow_fallback=1, and an explicit d3d11va device. This hybrid NVIDIA/Intel
  display environment does not expose a usable Desktop Duplication output to
  FFmpeg. Switching backends would break capture on this machine, so gdigrab
  was kept. (Inference: the failure is environment/driver-specific, not a
  Kenta defect.)
- `-zerolatency` made NVENC initialization fail; `-surfaces 4` produced no
  measurable change.
- `ffmpeg -encoders` costs 34 ms per spawn; dshow device enumeration costs
  314 ms. Encoder enumeration was repeated on settings/capture paths.

8.3 CHANGES IMPLEMENTED
------------------------------------------------------------
Reliability
- src-tauri/src/process.rs: creates a Windows Job Object with
  JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE and assigns every capture/export FFmpeg
  child to it. Force-killing Kenta now kills FFmpeg with it.
- src-tauri/src/instance.rs: named-mutex single-instance guard. A second launch
  focuses the existing window and exits instead of starting a second encoder.
- capture::cleanup_stale_sessions: removes every pre-existing session directory
  at startup. The single-instance guard makes all such sessions stale.
- run_ffmpeg now spawns, contains, and waits instead of using .output(), so
  exports and thumbnails are contained too.

Performance
- Segment-list caching: status polling runs twice per second and previously
  re-read segments.csv and re-stat'd every segment each time. It now skips the
  parse when (mtime, length) is unchanged.
- Encoder-list caching with explicit invalidation from "recheck FFmpeg".
- Release profile: codegen-units=1, lto=true, strip=true.

Packaging / correctness
- Removed unused Rust dependencies tokio, ctrlc, and the windows crate
  (windows-sys is the crate actually used); added Win32_Security and
  Win32_System_JobObjects features.
- Removed unused npm dependencies clsx and cmdk (27 packages).
- Removed "cdylib" from the lib crate type. On Windows it produced a 14.4 MB
  app_lib.dll that the desktop exe never loads, yet Tauri's MSI bundler shipped
  it. Desktop builds still link the same code through the rlib.
- tauri.conf.json: beforeDevCommand/beforeBuildCommand used ";" which cmd.exe
  does not treat as a separator; changed to "&&". The MSI build previously
  failed at this step.
- web/index.html: favicon pointed at the nonexistent /vite.svg, causing a
  404 fallback on every launch; now /favicon.svg.

9.1 THE VISIBLE TERMINAL
------------------------------------------------------------
Symptom
  A console window stayed on the desktop for as long as Kenta was
  running, and short-lived probes flashed one during startup and while
  opening the clip library.

Cause
  Kenta itself has no console: main.rs sets windows_subsystem =
  "windows" for release builds. But ffmpeg.exe and ffprobe.exe are
  console programs, and Windows gives a console child of a GUI process
  a fresh console host with a visible window. Process inspection
  confirmed it: conhost.exe (PID 24200) was a direct child of the FFmpeg
  process (PID 22908) that Kenta had started.

Fix
  src-tauri/src/process.rs gained hide_console(&mut Command), which sets
  CREATE_NO_WINDOW (taken from windows-sys instead of a literal). It is
  applied at every child spawn:

    ffmpeg.rs   run_ffmpeg          exports
    ffmpeg.rs   ffprobe_available   startup probe
    ffmpeg.rs   ffmpeg_available    startup probe and explicit recheck
    ffmpeg.rs   video_encoders      settings, capture start
    ffmpeg.rs   audio_devices       settings
    ffmpeg.rs   probe_duration      export validation
    capture.rs  replay encoder      the long-lived child
    commands.rs run_thumbnail       clip library

  explorer.exe is a GUI program and is deliberately untouched.

Verification
  With the app running and buffering, an EnumWindows sweep found zero
  visible windows of class ConsoleWindowClass or
  CASCADIA_HOSTING_WINDOW_CLASS. The FFmpeg console host still exists,
  as Windows requires, but reports 0 visible windows. Capture keeps
  working: one ffmpeg.exe child, buffer growing, 32/32 unit tests pass.

9.2 WHY SECTION SWITCHING FELT SLOW
------------------------------------------------------------
What it was not
  A CDP profile of the running app measured click-to-content at 9-10 ms,
  click-to-paint at 16-56 ms, no long tasks, and 8.3 ms frames. GPU
  status reported hardware compositing (ANGLE/D3D11 on the RTX 3050 Ti,
  DirectComposition enabled), so neither the main thread nor the
  compositor was the bottleneck.

What it was
  1. A 280 ms view-in animation (fade plus a 6 px slide) ran on every
     mount, so a section looked unsettled for a third of a second after
     it had already painted.
  2. Every view unmounted on switch. Clips threw away its list and
     regenerated thumbnails; Settings re-ran DShow device enumeration
     (about 300 ms), encoder enumeration, and monitor enumeration.
  3. Selecting Clips bumped refreshToken, so the list refetched even when
     nothing had changed.
  4. listClips always waited 180 ms before issuing its request.
  5. capture-status arrives every 500 ms and re-rendered the whole clip
     grid and the settings form, even while they were hidden.
  6. Both buffer bars animated width, relaying out on every tick.
  7. The topbar carried a backdrop-filter blur even though it is a flex
     sibling of the scroll area and nothing ever moves behind it.

Fixes
  - Sections mount on first use (on click, or on pointer or keyboard focus
    over the nav item) and are then kept mounted, hidden with [hidden].
  - ClipsView and SettingsView are memoised; the status tick no longer
    re-renders either of them.
  - The clip list is no longer refetched on navigation, and no longer
    waits 180 ms unless the user is typing in the search box.
  - The view transition is a 120 ms fade with no movement.
  - Buffer bars animate transform: scaleX instead of width.
  - The topbar blur is gone.
  - Thumbnails decode asynchronously and generate two at a time.
  - The clip preview closes when its section is left, so an autoplaying
    video cannot keep producing sound behind another view.
  - Unreferenced leftovers from the Vite template were deleted
    (App.css, react.svg, vite.svg, hero.png, public/icons.svg).

After
  click-to-content    5-8 ms
  click-to-paint      15-23 ms
  long tasks          none
  remount on switch   none (verified with an element identity marker)
  warm startup        35-52 ms
  release exe         8,433,152 bytes
  unit tests          32 passed

10.2 AUDIO STRUCTURE (WHAT THE EDITOR EDITS)

Recording no longer mixes sources at capture time. Each enabled source is
written as its own AAC stream inside the MP4 and tagged with a stream
title:

  PC audio only        one stream, title "PC Audio"
  Microphone only      one stream, title "Microphone"
  Both, same device    one stream, title "Mixed Audio" (deduplicated)
  Both, distinct       two streams, titles "PC Audio" and "Microphone"

The editor probes the file and reads those titles (FFmpeg 9 stores the
stream title as the MP4 "name" tag, so both keys are accepted). A file
with two distinct titles gets three lanes: Video, PC Audio, Microphone.
Anything else - legacy clips, untitled streams, or a partly tagged file -
gets two lanes: Video and Mixed Audio, where the mixed lane is every audio
stream combined.

Export re-encodes rather than stream-copies. The filter graph trims each
track, resets timestamps, concatenates the kept pieces with explicit
black video and anullsrc silence for gaps, then mixes the audio tracks.
Re-encoding is deliberate: it makes a gap, a split, and a moved segment
exactly what the timeline says, at the cost of encode time.

The original file is only ever read. An export writes a new file beside
it as <stem>_edited.mp4, with _1, _2, ... if that name already exists.
The result is probed, then registered in the library with source
"edited"; the library shows an "Edited" badge.

10.3 SAVED-CLIP EDITOR

Entry point
  Edit is offered on saved clips in the library. It loads only that clip,
  releases the player and the probe process on exit, and Back or Close
  returns to the library with the previous section state intact.

Editing
  One shared ruler and playhead across all lanes. Split at the playhead,
  delete a selection, trim an edge, move a segment, undo and redo. Invalid
  ranges and overlaps are rejected instead of silently corrected. A gap
  is black video plus silence, never a frozen frame or a stretched clip.

Saving
  Save shows progress and can be cancelled. The export command is
  declared async, so Cancel is not queued behind the encode: a cancelled
  export stops in well under a second and leaves no partial file and no
  success toast. The clip is validated before it is registered.

No capture interaction
  Opening, editing, exporting, and closing the editor never enumerate
  devices and never restart capture. Capture stayed "Buffering" through
  every editor run.

10.4 VOICE CLIPPING

Recognition
  In process, using the speech engine Windows already ships (SAPI5). The
  grammar is generated from the two configured phrases, written to a
  temporary file, loaded as a static command grammar, and the file is
  deleted immediately. Nothing is uploaded.

State machine
  The wake phrase arms a six-second window; the clip command inside that
  window triggers one save. Matching is whole-word at both ends, so
  "clipping that" does not match "clip that". A recognition below the
  confidence threshold is ignored, and a trigger inside the cooldown is
  dropped, so one spoken command cannot save twice.

Saving
  A trigger calls the same perform_save_replay path as the hotkey, so the
  clip length clamp, the library registration, the confirmation chime,
  and the exporting guard are identical. A live recording is never cut
  short, and voice refuses to save while the buffer is not running.

Status and test
  States: disabled, initializing, ready, unavailable, buffer-not-ready.
  Status is pushed to the UI as a "voice-status" event, so the settings
  badge follows the engine without polling. The Test button listens for
  one utterance (2-15 s), reports what was heard and whether it matched,
  and never saves a clip.

Defaults and language
  Off by default. Wake "Kenta", command "clip that", 30 s clip, 60%
  confidence, 5 s cooldown. The recogniser language follows the UI
  language and falls back to en-US with a visible note; if no recogniser
  exists the state is "unavailable" with the reason.

No focus steal
  Verified with Notepad in the foreground: the engine restarted and
  reached "Ready - en-US" while Notepad kept focus, and capture stayed
  buffering.

10.5 SAVE CONFIRMATION CHIME

The chime is generated in memory as a short WAV - there is no asset file
to lose. It is played on a short-lived worker thread with
PlaySound(SND_MEMORY | SND_NODEFAULT); volume is applied by scaling the
samples, and 0 is truly silent. It fires only after a save has succeeded
(replay save, manual recording stop, or editor export), once per save,
never on failure or cancel, and never blocks the save path.

Preview auditions the draft volume without saving settings. The settings
section has enable, volume, and preview; the values persist and are
restored after restart.

The chime is played after the clip is finalised, so it is not part of the
saved clip. One interaction is unavoidable: if desktop/PC audio capture
is enabled and the default playback device is also the device being
loopback-captured, the chime can land in the next replay buffer. It
cannot land in the clip that was just saved. This is documented in the
UI rather than hidden.

10.6 PRIVACY AND DATA HANDLING

  - No network calls. Recognition is in process.
  - No audio is stored: the recogniser consumes the microphone stream and
    the samples are discarded.
  - No transcript is stored. The last heard phrase and confidence exist
    only in memory, for the status badge, and are gone on restart.
  - The grammar file is deleted immediately after it is loaded.
  - settings.json stores only the phrases, lengths, thresholds, and the
    chime preferences.

10.8 LIMITATIONS AND HONEST GAPS

  - The microphone on this machine does not reliably hear the speakers, so
    live speech was only reproducible once. The deterministic proof is the
    WAV-fed engine test, which uses the same session, grammar, and event
    loop as the microphone.
  - No PC-audio loopback device was available here, so the PC Audio lane
    was verified with synthetic media carrying the same tagged streams,
    not with a real loopback recording.
  - SAPI needs an installed speech language. Without one the feature is
    unavailable, and the UI says so instead of pretending to listen.
  - The editor re-encodes, so an export takes about as long as encoding
    the kept range. Progress and Cancel are always available.
  - Recognition quality depends on the Windows recogniser and microphone;
    the confidence threshold is the only tuning knob.
  - The chime/loopback interaction in 10.5 is inherent to capturing the
    same output device and cannot be removed in software.

Housekeeping
  The two test clips were deleted through the app, and the library is
  empty. The original clip used for editor verification now exists only
  in the user's own .zip archive in the output folder; at verification
  time the editor had left its SHA-256 and modification time unchanged.

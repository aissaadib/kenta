Method

    kept (it is consistently the slowest because WebView2 caches are cold).
    Metrics: process launch -> main window handle, -> CDP endpoint ready,
    -> .app-shell present (usable UI), plus in-page navigation/paint entries.
    WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222 was set
    for both the before and after runs.
  - Navigation, preview, editor, save and recording were driven through the
    running UI over CDP, measuring DOM and next-paint times in the page.
  - Memory is the whole process tree (kenta + WebView2 children), with
    FFmpeg reported separately, because the encoder dominates the total.
  - Voice CPU was sampled at 1 s intervals as a percentage of one core.
  - Every change was kept only after the same benchmark was repeated.

2. FINDINGS
-----------

2.1 Confirmed opportunity: startup was gated on the first buffer segment

  Evidence: 2.56-2.73 s inside engine.start(), 3.0-3.4 s in initialise(),
  and a 4.0 s window. Moving only that call to a worker thread (temporary
  build) produced a 1468 ms window median, proving the wait was the cause.
  Fix: start capture on a named worker thread; add capture_starting so
  commands wait instead of racing the worker; report "Starting" while the
  engine does not exist yet; wait for the worker during shutdown so its
  FFmpeg child is dropped rather than orphaned.
  Benefit: window 4045 -> 877 ms, usable UI 3998 -> 827 ms, FCP 3080 -> 348 ms
  (medians). The buffer still becomes ready ~2.6 s after launch, by design.
  Risk: low. start() is unchanged and still synchronous for explicit starts
  and settings saves; the only new state is a bounded wait (6 s commands,
  12 s shutdown).
  Proving test: the same 3-run startup script plus an exit-during-startup
  test (see 4.3).

2.2 Confirmed defect (functional, fixed): audio exports used global indices

  Evidence: a clip with one video stream and one audio stream failed with
  "Error binding filtergraph inputs/outputs: Invalid argument" because the
  graph asked for [0:a:1]. A two-source clip selected the wrong source.
  FFprobe reports a global stream index; FFmpeg's [0:a:N] counts audio
  streams only.
  Fix (ea1a40a): classify_audio stores audio-relative positions; the mixed
  layout lists 0..audio.len(); tests updated and a single-untagged-audio
  regression test added.
  Benefit: export works for every layout that used to fail, and two-source
  edits no longer swap PC audio and microphone.
  Risk: low; pure index translation, covered by unit and real-FFmpeg tests.
  Proving test: real export of the 20 s clip succeeded end to end, and the
  synthetic integration test now exercises the single-audio path.

2.3 No meaningful issue: navigation, preview, editor, save, recording, voice

  - Navigation stayed at 2.3-5.4 ms DOM and 19-23 ms paint after the change;
    no long tasks. JS heap stayed in the single-digit MB range across the
    whole session (peak 6.2 MB); no unbounded growth was observed.
  - Preview open/close is unchanged (2-11 ms element, 29-158 ms playing,
    20-23 ms close) and the video element is released on close.
  - Save replay is unchanged (373-439 ms) and the chime fires once.
  - Manual recording start (60 ms) and stop -> saved (3.73 s) are unchanged.
  - Voice CPU is unchanged in practice (1.33% mean ON after the change vs
    1.14% and 0.94% in two baseline samples; OFF was 0.42%).
  - No orphan FFmpeg, temp sessions or duplicate encoders after repeated
    start/stop, saves, previews, editor opens, export and cancel.

2.4 Needs evidence / left alone: bitrate overshoot on high-motion content

  20 s replay clips were 43.6-45.8 MB (17.5-18.2 Mbps) despite
  -b:v 8000k -rc vbr -cq 23, while a static-desktop recording was
  0.58 Mbps. The CQ ceiling dominates on busy content. Changing the encoder
  flags would change quality and behaviour, so this is reported as a disk
  usage characteristic, not fixed.

6. REMAINING LIMITATIONS
------------------------

  - "Cold start" here means a fresh process with warm OS and WebView2
    caches. A true post-reboot cold start was not measured (it needs a
    reboot); the first run of every set is reported separately for that
    reason.
  - The packaged MSI was not rebuilt or re-measured after the two commits;
    all numbers are the release binary with embedded production assets.
  - The hotkey path during the 2.6 s startup window was not exercised with
    a real global shortcut, but it goes through perform_save_replay /
    perform_toggle_manual, which now wait for capture_starting.
  - An explicit "Start buffer" is still synchronous (~2.5 s) and shows the
    idle state with a disabled button while it runs. Only the startup path
    was moved off the setup thread; changing the explicit path would alter
    existing behaviour for no measured startup gain.
  - Voice recognition can pick up ambient speech; the log showed a wake
    phrase during testing. The user's voice setting was restored and left
    unchanged.
  - rustfmt is not installed for this toolchain, so no formatting check was
    run; the edits follow the surrounding style.
  - The editor re-encodes on export, so duration is roughly the kept range;
    that is by design and was not changed.
